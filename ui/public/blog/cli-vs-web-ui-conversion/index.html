CLI vs. Web UI: Which open-context Interface to Use

Use open-context's CLI when you want to script a conversion, batch-process several ChatGPT exports, or run inside Docker and CI with no browser involved. Use the web UI when you want to upload a ZIP, preview conversation titles and counts, and review or hand-edit the generated preferences before exporting. Both interfaces call the exact same parsing pipeline, so the output — markdown conversations, preferences.md, and memory.md — is identical either way; the only thing that changes is how you trigger it.

Key takeaways

  • The CLI's convert command and the web UI's POST /api/convert endpoint both run the same ChatGPTParser → ConversationNormalizer → MarkdownFormatter pipeline, so conversion quality is never a reason to pick one over the other.
  • The CLI writes directly to disk — conversations/, index.md, preferences.md, memory.md — with no server process required, which makes it the better fit for scripts, cron jobs, and batch loops over multiple exports.
  • The web UI needs the Express server running (npm run server or the Docker image's default command) and returns the same data as JSON for the dashboard to render as a reviewable pipeline before you export anything.
  • Both honor --skip-preferences / skipPreferences to bypass Ollama analysis entirely for an instant, model-free conversion.
  • The official Docker image bundles all of it, so switching between CLI and web UI is a matter of which command you pass to docker run, not which image you pull.

Same pipeline, two front doors

It's easy to assume the CLI and web UI are two separate tools that happen to share a name. They aren't. src/index.ts's convert command and src/server.ts's /api/convert route handler both extract the ZIP with the same ZipExtractor, parse conversations.json with the same ChatGPTParser, and normalize every message with the same ConversationNormalizer. Preferences and memory come from the same OllamaPreferenceAnalyzer, falling back to the same basic, model-free generator if Ollama analysis fails or is skipped.

That means picking between them is purely a workflow decision — terminal versus browser, disk files versus a reviewable dashboard — not a tradeoff in what actually comes out the other end.

Where the CLI wins

Scripting and batch jobs

The CLI's convert command takes exactly one ZIP per call and no glob support, so converting several exports means looping over it from a shell script — covered in more detail in Batch-Converting Multiple ChatGPT Exports With the CLI. That pattern only works cleanly with a command-line tool: there's no equivalent of dragging ten ZIP files onto a browser upload field and getting ten separate output folders back.

No browser, no server

npm run dev convert path/to/export.zip (or the compiled node dist/index.js convert) runs end to end in one process with no Express server, no port, and no React build. That's exactly what you want in a CI job or a one-off terminal session where spinning up a web server would be overhead with no payoff.

Fast, model-free conversion

Add --skip-preferences and the CLI skips Ollama entirely, writing the markdown conversion in seconds. It's the quickest path to a plain conversion when you don't need AI-written preferences at all — for example, when you only want the conversations/ folder as project knowledge.

Where the web UI wins

A visual review before you trust the output

The web UI's ContextViewer and pipeline components list every conversation with its title, message count, and dates before you commit to exporting anything. Preferences and memory generated by Ollama can be wrong or thin depending on the model and export size — the dashboard lets you read them before pasting them into Claude, something a terminal log scrolling past doesn't make easy.

Hand-editing preferences, not just generating them

If the AI-generated preferences.md gets something wrong, the web UI's six-section PreferencesEditor — covered in Inside the 6 Sections of the open-context Preferences Editor — lets you fix it with form fields instead of hand-editing markdown. The CLI has no equivalent; its output is the final artifact, not a draft you refine in place.

One image, but the UI needs the server up

The same Docker image that runs the CLI also serves the web UI, but only when its default command (node dist/server.js) is running — see One open-context Docker Image, Three Ways to Run It. If you've overridden the container command to run the CLI or the MCP server instead, the dashboard simply isn't reachable until you switch back.

Decision table

ScenarioBetter fit
One personal ChatGPT export, first time using open-contextWeb UI
Converting exports from a dozen teammates in a loopCLI
Running inside CI or a cron job with no displayCLI
Reviewing or correcting AI-generated preferences by handWeb UI
Skipping AI analysis entirely for a fast raw conversionEither — same flag
Scripting against the conversion without a browserCLI, or curl against the UI's API

That last row matters: because /api/convert accepts a plain multipart upload and returns JSON, you don't strictly need the browser to use the web UI's endpoint — you can curl a file to it from a script. It's a legitimate middle ground when you want the server's JSON response shape without opening a tab.

What stays identical either way

Privacy and output format don't change based on which interface you pick. Both run entirely on your own machine; the only outbound network call either one can make is to an Ollama instance you control, and only if preference analysis isn't skipped. The normalized conversation schema — role, content, timestamp, attachments — and the resulting markdown files are byte-for-byte the same shape whether you typed a command or dragged a file into a browser.

FAQ

Do the CLI and web UI produce different output?

No. Both call the same ChatGPTParser, ConversationNormalizer, and MarkdownFormatter pipeline, so the conversation markdown, preferences.md, and memory.md content is identical either way — only how you trigger the conversion differs.

Can I use the CLI from inside the official Docker image?

Yes. The same adityakarnam/open-context:latest image that defaults to the HTTP server can run the CLI instead by overriding its command to node dist/index.js convert <file>, with no separate image or rebuild needed.

Does the web UI need a running server?

Yes. The web UI is a React dashboard that uploads your export ZIP to a POST /api/convert endpoint on open-context's Express server, so the server process has to be running — either via npm run server or the Docker image's default command.

Can I call the web UI's conversion endpoint without opening a browser?

Yes. POST /api/convert accepts a multipart file upload and returns normalized conversations, preferences, and memory as JSON, so you can script against it with curl or any HTTP client instead of using the dashboard.

Which interface should I use for a single personal ChatGPT export?

The web UI is usually the better fit for a one-time personal migration, since it lets you preview conversation titles and counts and edit the generated preferences before exporting. The CLI is faster if you're already comfortable in a terminal and don't need a visual review step.
