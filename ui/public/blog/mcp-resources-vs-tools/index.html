MCP Resources vs. Tools: Why open-context Uses Only Tools

MCP defines three primitive types, split by who decides when to use them: tools, which the model invokes on its own; resources, which the host application attaches to context; and prompts, which the user triggers explicitly. open-context's MCP server exposes 13 tools and zero resources, because every operation it needs — saving a memory, recalling it, searching across bubbles — depends on the model deciding mid-conversation that it's needed, not on the client deciding ahead of time what to attach.

Key takeaways

  • The MCP 2025-11-25 spec assigns tools to model control, resources to application control, and prompts to user control.
  • open-context's MCP server (src/mcp/server.ts) registers 13 tools — six legacy context tools, five bubble tools, and two canonical v2 context tools — and defines no resources at all.
  • Resources fit data the host app decides to attach regardless of what the model asks for; open-context's job is reactive memory the model calls on demand, which is what tools are for.
  • All 13 tools sit on the same pluggable BYODB store, so the tools-vs-resources choice is independent of which of the 15 supported databases backs it.
  • A resources-based recall_context would move the "should I pull this memory back up" decision out of Claude's hands and into the client's — the opposite of what persistent memory needs.

The three MCP primitives, and who decides when to use them

MCP (Model Context Protocol) gives servers three ways to expose capability to a client, and the spec's own framing sorts them by who is in the driver's seat. The official specification describes tools as model-controlled: the language model discovers them and decides, from context and the user's request, when to call one. Resources are application-controlled: the client or host app chooses what to attach to the context window, independent of the model's own reasoning. Prompts are user-controlled: templates the user invokes explicitly, like a slash command.

That control split is a design recommendation, not a protocol requirement — a server is technically free to expose the same data through either primitive — but it's still the right lens for deciding which one fits a given job. If the decision to use a capability should come from the model reasoning about a request, it belongs in a tool. If it should come from the host application attaching context regardless of what the model is doing, it belongs in a resource.

What open-context's MCP server actually exposes

open-context's MCP server (src/mcp/server.ts) is built on @modelcontextprotocol/sdk and defines exactly one kind of capability: tools. There are 13 of them, each registered with server.tool(), and not a single server.resource() call anywhere in the codebase:

  • save_context, recall_context, list_contexts, search_contexts, update_context, delete_context — the original six, covering memory CRUD plus full-text and multi-keyword search.
  • create_bubble, list_bubbles, get_bubble, update_bubble, delete_bubble — project-scoped workspaces that group related contexts (see Tags vs. Bubbles for how that grouping works).
  • save_canonical_context, query_canonical_context — the newer v2 interface, backed by the same @opencontext/core canonical schema the CLI and web UI share.

Every one of those is something Claude decides to call based on what's happening in the conversation — "remember this," "what did I say about X," "show me everything tagged project-alpha" — not something the client application decides to attach up front. See the full tools reference for what each one does and when Claude typically calls it.

Why a memory server is tools-shaped, not resources-shaped

The giveaway is in the verbs. save_context and recall_context exist because the moment to act is unpredictable: a user might ask Claude to remember something three messages into an unrelated conversation, or ask "what did I tell you about my deploy process" at any point without warning. Only the model, reasoning over the live conversation, knows when that moment has arrived. A resource can't make that call — resources are meant for the client to attach proactively, like "always include the current file" in an IDE, not for "attach this if and only if the model realizes it's relevant."

That's also why open-context's tools take a query or content payload as an argument rather than exposing memory as a browsable URI tree. recall_context and search_contexts behave like a search function, not a file listing — the model supplies intent, the tool returns a result, and the model decides what to do with it next.

Where resources would actually be the better fit

None of this makes resources the wrong primitive in general — it means they're the wrong primitive for this particular server. Resources earn their place when the data to attach doesn't depend on the model noticing it's relevant: a fixed project README a host wants in every session's context, a live log tail a dashboard subscribes to, or a config file an IDE extension always wants visible regardless of what the user typed. In those cases the application already knows the data belongs in context, so making the model ask for it through a tool call just adds a round trip for no benefit.

If open-context ever shipped a feature like "always surface my active bubble's five most recent contexts at the start of every session," that's exactly the shape of an application-controlled resource, not a model-controlled tool — the client would decide to attach it before the model ever reasons about whether it's needed.

The tools-vs-resources choice is separate from the storage choice

It's worth separating this from a different design decision open-context also made: which database backs the context store. BYODB lets the same 13 tools run against any of 15 supported backends — JSON file, SQLite, Postgres, MongoDB, DynamoDB, and more — through one adapter interface. Swapping the backend never changes whether a capability is exposed as a tool or a resource; that choice is about how Claude is allowed to use the data, not where the data physically lives. A future resources-based "pin this context into every session" feature could sit on top of the exact same store without touching the tool definitions at all.

FAQ

What's the practical difference between an MCP tool and an MCP resource?

A tool is something the model decides to call based on the conversation; a resource is something the client or host application decides to attach to context regardless of what the model is doing. The MCP spec labels this model-controlled versus application-controlled.

Does open-context's MCP server implement any resources?

No. Its server (src/mcp/server.ts) registers 13 tools via server.tool() and contains no server.resource() calls — every capability it exposes is something Claude chooses to invoke.

Why not expose recall_context as a resource instead of a tool?

Because the decision to pull a memory back into context has to come from the model noticing it's relevant mid-conversation, not from the client attaching it ahead of time. That decision-making pattern is exactly what MCP tools are for.

Does having 13 tools instead of 6 cost more tokens or slow Claude down?

Tool definitions do add to the context sent with each request, but it's the same tradeoff any MCP server with multiple tools makes. open-context keeps each tool narrowly scoped to one CRUD operation rather than one large multi-purpose tool, which keeps individual descriptions short even as the count grows.

Could an MCP server mix tools and resources together?

Yes — the spec supports exposing both, and many servers do, pairing model-invoked actions with application-attached reference data. open-context's current use case just hasn't needed a resource yet.
